Session 1 · AI-Native PRD

What a Traditional PRD Misses

A traditional PRD specifies: what, who, why, how to build. For AI products, that is necessary but insufficient.

"An AI feature has probabilistic output — it doesn't always do the same thing to the same input. The spec has to account for this."

A traditional PRD asks: "What should the feature do?"

An AI-native PRD asks: "What should it do, how often must it get it right, what counts as wrong, and how will we know the difference?"

Writing "the agent should respond helpfully" is not a spec — it is a hope. A hope is not shippable.

Session 1 · AI-Native PRD · The Four Sections

The 4 AI-Native PRD Sections

Every AI feature PRD needs these four sections in addition to standard product sections — problem, user stories, acceptance criteria.

1 · Input / Output Contract

What exactly goes in. What format comes out. What output types are valid. What is explicitly out of scope.

2 · Quality Criteria

Measurable thresholds — never adjectives. Not "helpful." Always "≥ 92% accuracy on standard tickets." A number the team can test against.

3 · Failure Modes + Fallbacks

What happens when the agent gets it wrong — for each failure mode. Who catches it. What the customer sees while it is being caught.

4 · Eval Plan

How you will know it is working — before launch (offline evals on labeled data) and after (live monitoring). Who owns this and when it gates shipping.

Session 1 · Quality Criteria

What "Measurable" Actually Means

If your quality criterion cannot be checked with a number and a test set, it is not a criterion — it is an aspiration. Aspirations do not gate launches.

WRONG — Adjective specs. Not shippable.

· "The agent should respond helpfully"

· "Responses should be accurate"

· "The classification should be good"

RIGHT — Measurable thresholds. Shippable.

· Classification accuracy ≥ 92% on Order Issue tickets in the validation set

· ESCALATE recall ≥ 95% — miss at most 5% of complaints needing human review

· First-contact resolution rate ≥ 70% within 2 hours, measured on live traffic

Session 1 · Roles in AI Product Development

Who Owns What

Clarity on ownership prevents the two most common failure modes: PMs over-specifying architecture, or engineers under-specifying quality.

PM Owns — Product Decisions Engineering Owns — Tech Decisions
1. What is the quality bar?
The number. The metric. The threshold below which we do not ship.		 1. Architecture and model selection
Which model, which framework, fine-tune vs. prompt-only.
2. Which failure modes are unacceptable?
The non-negotiable cases. What zero-tolerance looks like before and after launch.		 2. Latency tradeoffs
Multi-step pipeline speed vs. quality optimization per step.
3. Where does human review sit?
HITL placement: before send, after send, or on escalation only.		 3. Infrastructure for evals
Test harness, eval pipeline, monitoring setup, alerting.

The PM cannot specify architecture. The PM must specify quality — because quality is a product promise to the customer.

Build 1 · Where it breaks

Where Does the Pipeline Break?

Every pipeline has a first failure mode. Knowing where it is before launch is the PM's job — not the post-launch incident review's job.

Session 1 · Build 2 · Step 4 — Reflection

Step 4 — Reflection: The Self-Checking Step

You are a quality reviewer for Wren CX.

Review this draft response before it is sent to a customer.
For each item in the checklist, flag a violation if it is found.
If any check fails, rewrite the response to fix it.

Checklist:
1. Does it make any specific timeline promises? (not allowed)
2. Does it mention a specific refund amount? (not allowed)
3. Is it under 75 words?
4. Does it end with a clear offer to help further?

Return JSON:
{
  "approved": true | false,
  "issues": ["list any violations found"],
  "revised_draft": "corrected response, or original if approved"
}

Draft to review: {draft}

This step prevents: timeline promises, refund commitments, responses that exceed 75 words, and responses that close without extending help. These are exactly the support agent liabilities your legal team cares about.

Session 1 · Build 2 · Tool-Use — CRM Lookup

Adding Tool-Use: Real Data Before the Draft

The Tool Call

tool:   get_order_status
params: {
  order_id:    "WR-84221",
  customer_id: "C-44192"
}

returns: {
  status:       "IN_TRANSIT",
  carrier:      "Delhivery",
  eta:          "2024-06-28",
  last_scan:    "Mumbai Hub",
  tracking_url: "https://track.delhivery.com/..."
}

What It Changes

Without tool-use — generic:
"Your order is being processed. Please allow 5–7 business days for delivery and check your email for updates."

With tool-use — specific:
"Your order WR-84221 is in transit with Delhivery and expected by 6 October. Track it here: [link]. Let me know if there's anything else I can help with."

Tool-use converts a generic AI response into a specific, grounded, trustworthy answer. This is the difference between a chatbot and an agent.

8:28 PM · PRD Review Board

PRD Review Board

Before engineering starts, your PRD has to survive five critical perspectives — not just one stakeholder sign-off.

Session 1 · PRD Review Board

Five Perspectives Before Engineering Starts

Each reviewer brings a different definition of "this is not ready." The PM's job is to survive all five before the first sprint.

Reviewer Their Core Question Their Specific Concern with AI Products
CTO Is this architecture realistic? What is the tech risk? Is the eval plan actually buildable with our current infra?
Data Science What is the eval plan? Do we have enough labeled data? Who builds and maintains the test set?
Legal / Compliance What are the liability risks? DPDP implications for handling customer data? What if the agent makes a wrong commitment?
GTM / Sales Can we demo this? What is the sales narrative? How do we explain a 92% accuracy bar to enterprise brands?
CEO / Founder Does this move the metric that matters? What is the retention impact? What is the first signal of success we can show investors?
