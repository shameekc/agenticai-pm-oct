Session 2 · The eval problem

You shipped Wren's agent
three weeks ago.

Is it getting better or worse? How do you know?

Normal software fails loudly

The button breaks. The API returns a 500. You know.

An agent fails silently

A model update drops accuracy from 91% to 83%. Every reply still looks right, with a confidence score. You find out when CSAT falls, three weeks later.

What an eval actually is

An eval is an answer key, not “it looked good”

The question paperTest inputs: your golden set
The answer key, written before gradingExpected outputs
The pass markYour threshold, with a reason
The same overlay on every paperA runner that works without you

TKT-B's key says GATHER_INFO before the agent ever runs. Engineering applies the key; the PM writes it.

Four questions, four kinds of eval

Pass today is not pass next month

Unit · build time

Right on this input?

TKT-A → ORDER_ISSUE, ≥ 0.80, AUTO_RESOLVE.

Regression · every change

Still right after a change?

Rerun the golden set after any model or prompt change. Alert on a 2-point drop.

A/B · before a switch

Is B actually better?

Same tickets through both. Read the disagreements, not the averages.

Consistency · often skipped

Same answer twice?

Run each ticket 3 times. If the decision flips, every other score is noise.

A cheaper model can win on average and still miss the one injection. That's why the golden set has an adversarial row.

Where you evaluate

Offline before you ship. Online after.

Offline · on a fixed test set

Did we build it right?

  • Golden set, run before every release
  • Regression after any model or prompt change
  • A/B: same tickets through old and new

Safe, repeatable, cheap. But it only tests what you thought of.

Online · on live traffic

Is it working for real customers?

  • Sample 2% of live replies for review
  • Signals: CSAT, agent edits, human overrides of AUTO_RESOLVE, reopened tickets
  • Drift alerts: accuracy, escalation rate, confidence mix

Catches the real world: Hinglish at 2 AM, Diwali volumes. But it's slower, and customers feel the misses.

You need both. Every online failure becomes a new offline golden row, so it can't come back unnoticed.

How you score

Code first. A judge where code can't.

Code-based

Deterministic checks

classification == "ORDER_ISSUE"
len(draft.split()) <= 75
output matches JSON schema
no "refund" promise in draft

Fast, free, never disagrees with itself. Only for things you can check exactly.

LLM-as-judge

A rubric, scored by a model

“Is the tone empathetic?”
“Does every fact in the draft appear in the CRM record?” → PASS / FAIL + reason

Scales the fuzzy qualities. Use a different model from the agent, and test it against human labels first.

Human

Labels and spot checks

You label the golden set.
A CX lead reviews 20 live replies a week.

The ground truth for the other two. Slow and costly, so use it to calibrate, not to grade everything.

An untested judge is just another unvalidated model in your critical path. Session 3 builds one and checks it against your labels.

Every number needs a reason

Where does your threshold come from?

A clean run proves less than you think

0 misses in 40 tests means the miss rate is probably under 7.5%, not zero (the rule of three: 3 ÷ 40).

To claim under 1%, you need about 300 clean cases.

A threshold is a staffing decision

2,000 tickets × 20% × 4 min
= 27 hrs/day ≈ 3–4 reviewers

Gate 0.80 → 0.90 “to be safe”
2,000 × 35% × 4 min
= 47 hrs/day ≈ 6 reviewers

Shares going to humans are illustrative. Safer on paper, slower in the queue.
