Build a multi-agent system
in 9 prompts

Three rules

  • One step per prompt. Never “build the whole system”.
  • Every agent earns its box. Three-sentence test, or it's a tool call.
  • The state object is the contract. Agents talk only through it.

Running example: Wren's reference design

Supervisor routes and coordinates · Triage classifies, sets urgency · Resolution drafts using the CRM · QA checks the draft, independently · Escalation hands off to a human.

Prompt 1 · Load the spec

Give it your canvas, not a wish

Read canvas.md (our Agent Opportunity Canvas). Don't write any code yet.
Create AGENTS.md (CLAUDE.md if you're Claude Code) with:
- the goal in one sentence, and the system's input and final output (JSON)
- the agents we think we need: [supervisor, specialist 1, 2, 3]
- a first draft of the input and the final output (we formalise them in step 3)
- tools each agent MAY use (read or write), and tools NO agent may have
- routing rules and HITL triggers, with our numbers: [confidence gate], [₹ limit]
- our quality bar: [criterion + number + why that number]
Then list everything in the canvas that's ambiguous, as questions for us.
✓ Before you move on:answer its questions. Every number in AGENTS.md has a reason. Keep it short: it's re-read on every prompt.

Prompt 3 · Contracts before code

Define the input and output schemas first

Before any agent exists, write JSON Schemas
in schemas/:
1. input.schema.json: what enters the system;
   required vs optional, types, allowed values
2. output.schema.json: the final answer; an
   enum for every decision, confidence 0-1,
   required reasoning, injection_detected
3. one schema per tool: arguments, result,
   and error shape
4. state.schema.json: every shared field, its
   type, and the agent that owns it
Write 3 valid and 3 invalid payloads per schema
and a validate.py. Show me what it rejects.

Wren's output contract, as a schema (simplified)

{
  "type": "object",
  "required": ["classification", "confidence", "action",
               "injection_detected", "reasoning"],
  "properties": {
    "classification": { "enum": ["ORDER_ISSUE", "PRODUCT_QUERY",
        "RETURNS", "COMPLAINT", "BILLING", "UNKNOWN"] },
    "confidence": { "type": "number", "minimum": 0, "maximum": 1 },
    "action": { "enum": ["AUTO_RESOLVE", "GATHER_INFO",
        "ESCALATE", "REJECT"] },
    "draft_response": { "type": "string" },
    "injection_detected": { "type": "boolean" },
    "reasoning": { "type": "string", "minLength": 1 }
  },
  "additionalProperties": false
}

“≤ 75 words” can't be expressed in JSON Schema, so it's a code check in validate.py.

✓ Before you move on:you sign off the output schema. It's what the agent can commit to on your brand's behalf. Enums, not free text, for every decision; a missing required field must fail loudly.

Prompt 5 · State object, supervisor, specialists

Agents talk only through the state

No API key: the coding agent runs each agent

Use schemas/state.schema.json, plus step_count
and handoff_log. Every agent validates its input
and output against the schemas before handing off.
Make each specialist a sub-agent with its own
prompt and ONLY its tools (Claude Code:
.claude/agents/[name].md). If your tool has no
sub-agents, run each specialist's prompt in turn,
passing state.json between them.
Run input 1 end to end and show me state.json
after every handoff.

With an API key: an orchestrator script

Load the schemas in schemas/.
Write orchestrator.py: the supervisor reads
state, picks the next specialist, calls it with
its own system prompt and only its own tools,
validates the fields it wrote against the
schema, then loops. Stop when the supervisor
says done or step_count hits 7.
Log every handoff to traces/[task_id].jsonl.
✓ Before you move on:you can point at one handoff and say who wrote which field. A missing field is a silent failure between agents, so the schema check matters.
Prompt 6 · Guardrails at the handoffs

Failures happen between agents

Add guardrails in code, not only in prompts:
- tools: each agent can call ONLY its own tools; anything else returns an error
- state: reject a handoff whose fields don't match the schema; never pass raw
  customer text into another agent's instructions, only as a data field
- loops: max 7 steps across all agents; the same agent twice in a row with no
  new state → stop and escalate
- QA: the QA agent sees the draft and the policy, not the Resolution agent's
  reasoning, so it judges independently
- HITL: escalate when [QA score] < [0.85], [amount] > [₹10,000], or legal
  language appears; write what the reviewer sees to review_queue.json
Show each guardrail firing on one sample input.
✓ Before you move on:one input and one output guardrail caught live, plus one bad handoff blocked. That covers capstone deliverables 4 and 5.
Prompt 7 · Evals: per agent and end to end

Know which agent broke

Build evals/:
1. golden.csv: input, expected final output, why it's in the set (10+ rows);
   every row must validate against schemas/
2. end-to-end: run every row through the whole system; a judge scores the
   final output on [criterion 1..4], using a different model from the agents
3. per agent: for each row, compare each agent's state fields with the
   expected ones (e.g. Triage's classification) and report which agent was
   first to go wrong
4. consistency: run each row 3 times; list rows whose final decision flips
Print a table, the pass rate, and failures grouped by agent.

No API key? Ask the coding agent to run each row and fill the table. Slower, same learning.

✓ Before you move on:compare the judge with your own labels on 5 rows. If one agent causes most failures, fix that agent, not the whole system.
Prompt 8 · Red-team the system

Attack the seams, not just the inputs

Act as a red-teamer for our multi-agent system. Write 10 inputs most likely
to break it, including:
- instructions hidden in a tool result that one agent passes to the next
- two agents that disagree (Triage says routine, QA says risky)
- a handoff with a missing state field
- a case that makes the supervisor bounce between the same two agents
- [an edge case only our domain has]
Run them. For each failure: name the spec line it breaks, add it to
golden.csv, propose the smallest fix. Don't apply any fix yet.
✓ Before you move on:fix one, re-run the evals, and keep the before and after. “The failure we fixed because of our evals” is a slide in your presentation.

When the coding agent goes wrong

Six habits that save a weekend

  • Paste the error verbatim. Not “it doesn't work”.
  • “Explain which agent failed, and why, before changing anything.” Stops random rewrites.
  • “Run the evals and show me the output.” Make it prove the fix.
  • Commit after every green step. Undo is one command.
  • The collapse test: “Merge [agent X] into the supervisor and re-run the evals.” If quality holds, keep it merged.
  • No real customer data, no keys in files. Mock data only; keys in .env, never committed.

Read every diff before you accept it. You're the PM on this build, and the reviewer.
